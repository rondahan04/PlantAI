Path of one request

  1. App - Expo / React Native. Holds no API keys.
  2. Node server - plain http, one process. Holds every key, spends every credit.
  3. Providers - PlantNet, OpenAI, Google Places, Tavily, Firecrawl.
  4. Supabase - account, plant library, photos, and the scrape cache shared by all users.

Answer rate is end-to-end: of the nearby shops a user could plausibly be shown, the share that came back with a real product and price. It is lower than the read rate because most shops simply do not stock the plant.

Routes

Five endpoints plus the job poll. Only the nursery search is asynchronous.

POST /api/diagnosePhoto → species + health. Calls PlantNet, then OpenAI.
POST /api/nurseriesReturns a job id immediately. Reading a dozen shops is far longer than a request should be held open.
GET /api/nurseries/job/:idPolled until the scrape finishes.
POST /api/care-planGenus → watering, feeding, repotting for every growing medium at once.

GET /healthCache state, provider last-success, per-site scrape faults.

Diagnose a plant

Two provider calls, one round trip.

  1. App checks photo size first. Over the limit is refused on the spot with the size and the reason - it used to surface only after the upload failed, reported as a lost connection.
  2. POST /api/diagnose - photo goes to the server.
  3. PlantNet → species.
  4. OpenAI → same photo plus the species, back comes health, issues, care.
  5. User decides. Saving starts the watering schedule. Where the record lands is under Account & data.

Nursery search

The expensive flow, and the only asynchronous one.

  1. POST /api/nurseries - location plus plant name. A job id comes back at once.
  2. Google Places → nearby nurseries that have websites.
  3. Read each shop - Tavily when the page is usable as served, Firecrawl when it has to be rendered.
  4. OpenAI → product and price pulled out of the page text.
  5. Poll /api/nurseries/job/:id - results land on a map.

Care plan

One OpenAI call per genus per install - not one per plant.

  1. POST /api/care-plan - genus, and family if known.
  2. OpenAI, once → watering, feeding and repotting for every growing medium at once: potting mix, LECA, semi-hydro, the rest.
  3. App caches it forever - keyed on genus. Moving a plant from soil to LECA reschedules instantly, offline, with no second call.

Keyed on genus because two monsteras in the same mix want the same thing.

Account & data

Accounts are optional. There is no login wall - signing in only changes where the same library is kept.

  1. Logged out - every plant lives on the device. Nothing leaves the phone.
  2. Sign-in goes app → Supabase Auth directly. The Node server is not in this path and never holds the session.
  3. Existing plants are offered as a one-time import. Declining leaves them where they are.
  4. Writes go to Supabase first, the device second. A failed write never lands locally, so the phone cannot show a plant the account does not have.
  5. Photos live in a private bucket under the user's own folder, displayed through short-lived signed URLs. No permanent public link.
  6. Signing out wipes the mirror. Deleting the account cascades the rows and clears the bucket.

Row-level security is what makes the direct app-to-database path safe: every policy checks the row against the caller's own user id.

Scraping

Every nursery site runs one of a handful of platforms. Identify the platform and the right search URL is already known - no per-site parser.

  1. Fingerprint the homepage. cdn.shopify.com or /products/ → Shopify. wp-content → WooCommerce. wixstatic.com → Wix.
  2. Reuse that platform's search URL. Shopify /search?q=, WooCommerce /?s=&post_type=product, Wix /search?q=.
  3. Still unknown? Re-fetch rendered. Some storefronts build their markup client-side and show nothing to a static fetch.
  4. Still unknown? Ask OpenAI. Scripts and CDN hints go to the model to classify and guess a search URL. The answer is written to disk, so an unfamiliar platform is never paid for twice.

Who reads the page

Shopify, WooCommerce → TavilyPage arrives finished. Well under a second.
Client-rendered → FirecrawlOnly Firecrawl renders. Tavily is the rescue if it fails.

81s → 36.5s. Healthy shops went from 26-41s each to about a second. The cause was never concurrency - Firecrawl allows ten requests a minute, and a refused read looks exactly like an unrecognized platform, which is the path that spends three more requests on the same shop. The limit was feeding itself.

Health

GET /health answers what is otherwise invisible until it shows up on a bill or in a bad review.

Is the shared cache on?Without its Supabase credentials the cache answers "miss" forever. Nothing breaks, nothing is logged, and every search becomes a live paid scrape. cache.enabled says so outright.
Has a shop stopped parsing?Changed markup returns nothing forever while the search still "succeeds" - results are just quietly shorter. A site failed several times running is flagged. A shop read fine that merely lacks the plant is not a fault.
Which providers answer?lastSuccess per provider, so an outage is visible before a user hits it.

The summary is public. Per-site detail and the recent-failure ring need the shared secret - an open endpoint should not enumerate which shops we scrape or which are down.
