The stack, in one picture

Four lines and nothing else. The app talks to one server and to Supabase; only the server talks to a paid provider, because only the server has the keys.

Which API is called, and when

1Diagnose a photo Two providers, one round trip. Nothing is stored on the server.
  1. App resizes the photo, then POST /api/diagnose. Over the size limit is refused before a credit is spent.
  2. PlantNet /v2/identify/all → species, genus, confidence.
  3. OpenAI, only when the species is a coin-flip inside a confident genus → re-reads the photo to settle it.
  4. OpenAI again, photo plus species → condition, issues, treatments, care.
  5. One JSON answer back to the app.
2Nursery search The expensive flow, and the only asynchronous one.
  1. POST /api/nurseries with plant, lat, lng, radius → a job id at once.
  2. Supabase cache checked first. A recent identical search returns results inline and stops here.
  3. Google Places places:searchText → nurseries in the radius, boxed then cut to the true circle.
  4. Tavily /extract reads each shop. Firecrawl /v1/scrape only when the plain read comes back with no product grid.
  5. OpenAI → product and price pulled from the page text.
  6. GET /api/nurseries/job/:id polled until done; the result is written back to the cache for the next user.
3Care plan & Hebrew One model call each, then never again.
  1. POST /api/care-plan → OpenAI once per genus, answering for every growing medium in a single call.
  2. POST /api/translate-diagnosis → OpenAI turns the diagnosis text into Hebrew.
  3. Both land in expo-sqlite on the device, so switching medium or language afterwards is instant and offline.
4Account & data The one path the Node server is not on.
  1. @supabase/supabase-js calls Supabase straight from the app: Auth, library rows, photo bucket.
  2. The session belongs to the user, so routing it through the server would only add a second thing to trust.
  3. Writes go to Supabase first, device second — a failed write never lands locally.
  4. The server reaches the same project with a service-role key, but only for the shared scrape cache.
Why one server and not five clients

Keys. Anything compiled into an Expo bundle is readable by anyone who downloads the app. Five provider keys on the device is five keys given away, and every credit spent on them is billed to the project.

Caching. A scrape paid for by one user is worth nothing if the next user cannot see it. The cache only works because every search passes through the same process, keyed the same way.

One thing to watch. GET /health answers for all five providers at once. Spread across clients, an outage is only visible in the reviews.

Diagnose a plant

Two provider calls, one round trip.

  1. Size checked first. Over the limit is refused on the spot, with the size and the reason.
  2. POST /api/diagnose Photo goes to the server.
  3. PlantNet → species.
  4. OpenAI Same photo plus species → health, issues, care.
  5. User decides. Saving starts the watering schedule - see Account & data.

Nursery search

The expensive flow. The only asynchronous one.

  1. POST /api/nurseries Plant, location, radius. Job id at once - or finished results, if this exact search just ran.
  2. Google Places → nurseries in radius, boxed then cut to the true circle.
  3. Read each shop Tavily when served plain, Firecrawl when it must be rendered. Platform (Shopify, Wix, WooCommerce…) is remembered per host, so a returning shop skips identification entirely.
  4. OpenAI → product and price pulled from the page text.
  5. Poll /api/nurseries/job/:id Results land on a map.

4 things worth knowing

Cached across users. A recent scrape for that plant and place skips everything past step 2 - the next person's search costs nothing and takes seconds.

Platform remembered per host. Once a shop's identified as Shopify, Wix, WooCommerce or another platform, that mapping is written to disk - every later search for that shop reuses it instead of re-detecting.

Listed, stock not stated. A page with the plant and a price but no stock line is kept, not dropped - it might still sell the plant.

The radius is a promise. Places only biases location, so a Mitzpe Ramon search came back full of Tel Aviv. Now it's boxed to the circle first, then cut by distance.

Care plan

One OpenAI call per genus per install - not one per plant.

  1. POST /api/care-plan Genus, and family if known.
  2. OpenAI, once → watering, feeding, repotting for every medium at once: soil, LECA, semi-hydro.
  3. Cached forever Keyed on genus. Moving mediums reschedules instantly, offline.

Account & data

Accounts are optional. No login wall - signing in only moves where the library lives.

  1. Logged out Every plant stays on the device.
  2. Sign-in App → Supabase Auth directly. The Node server is never in this path.
  3. Existing plants Offered as a one-time import. Declining leaves them where they are.
  4. Writes Supabase first, device second - a failed write never lands locally.
  5. Photos Private bucket, short-lived signed URLs. No permanent public link.
  6. Sign out / delete Wipes the mirror. Deletion cascades the rows and clears the bucket.

Scraping

Every nursery site runs one of a handful of platforms - identify it and the search URL is already known.

  1. Fingerprint the homepage. cdn.shopify.com → Shopify. wp-content → WooCommerce. wixstatic.com → Wix.
  2. Reuse that platform's search URL. Shopify /search?q=, WooCommerce /?s=&post_type=product, Wix /search?q=.
  3. Still unknown? Re-fetch rendered. Some storefronts build markup client-side.
  4. Still unknown? Ask OpenAI. Classifies from scripts/CDN hints. Written to disk - paid for once.

Who reads the page

Tavily leads. Every read.No JS execution, ~700ms. Tries first even on sites that want a render - Firecrawl's 10/min window is the scarce resource.
Firecrawl is the rescueOnly it drives a real browser. Fires when Tavily's read comes back with no product grid - reliably what a client-rendered site (Wix, unknown platforms) gives an unrendered fetch.
81s → 36.5s - what changed

Never concurrency. Firecrawl allows ten requests a minute, and a refused read looks exactly like an unrecognized platform - the path that burns three more requests on the same shop. The limit was feeding itself.

Health

GET /health answers what's otherwise invisible until it shows up on a bill or a bad review.

Is the shared cache on?Without Supabase credentials, every search becomes a live paid scrape. cache.enabled says so.
Has a shop stopped parsing?Changed markup fails silently - several failures in a row gets flagged.
Which providers answer?lastSuccess per provider - an outage is visible before a user hits it.

Summary is public. Per-site detail needs the shared secret - an open endpoint shouldn't enumerate which shops get scraped.
