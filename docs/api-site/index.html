PlantAI Stack

What's used, and which API gets called when.

Diagram

APIs, tools & libraries

  • Expo / React Nativethe phone app itself
  • Node httpthe backend - no framework, one process
  • PlantNet APIidentifies the plant species from a photo
  • OpenAI (gpt-5.6-luna, vision)diagnoses health from the photo; writes the per-genus care plans; also extracts product info from scraped text

  • expo-notificationsschedules watering reminders

Flow 1 - diagnose a plant

  1. App takes a photo and checks its size before sending. Anything over the server's limit is refused on the spot, with the size and the reason - a photo too big to accept used to be discovered only after the upload had already failed, and reported as a lost network connection.
  2. App sends it to POST /api/diagnose.
  3. Server calls PlantNet → gets the species.
  4. Server calls OpenAI with the same photo + species → gets health, issues, care plan.
  5. The user decides whether to keep it. Saving adds the plant to the portfolio and starts its watering schedule; where the record goes - this device, or the account - is flow 4.

Flow 2 - find a nursery

  1. App sends location + plant name to POST /api/nurseries → gets a job id back right away, because reading a dozen shops takes far longer than a request should be held open for.
  2. Server calls Google Places → nearby nurseries with websites.
  3. For each one, the server reads the shop's search page - Tavily when the page is usable as served, Firecrawl when it has to be rendered first - then OpenAI to pull out product + price.
  4. App polls GET /api/nurseries/job/:id until it's done, then shows the results on a map.

A shop whose page lists the plant and its price but never says whether it is in stock is shown as listed, stock not stated rather than dropped. Removing it would hide a nursery that does sell the plant, on the grounds that the page did not prove it - saying what the page actually supports keeps the shop and keeps us honest.

Step 2 onwards is skipped entirely when Supabase already holds a recent scrape for that plant and location - the cache is shared across every user, so the second person to look for a monstera this week pays nothing and waits seconds instead of minutes.

Flow 3 - care advice for a plant you own

  1. App sends the genus (and family, if it knows it) to POST /api/care-plan.
  2. Server calls OpenAI once and gets back watering, feeding and repotting guidance for every growing medium at once - potting mix, LECA, semi-hydro, and the rest.
  3. App caches that answer forever, keyed on the genus. Switching a plant from soil to LECA reschedules it instantly and offline, with no second call.

Keyed on the genus rather than the plant, because two monsteras in the same pot mix want the same thing. In practice that makes this roughly one call per genus per install, not one per plant.

Flow 4 - the library follows the account

Accounts are optional and there is no login wall. Logged out, every plant lives in on-device storage and nothing leaves the phone. Signing in changes where the same library is kept.

  1. App signs in through Supabase Auth directly - the Node server is not in this path and never holds the user's session.
  2. If the device already has saved plants, the app offers to import them once. Declining leaves them exactly where they are.
  3. From then on every save, watering, repot and edit writes to Supabase first and only then to the on-device copy, which becomes a mirror rather than the source of truth. A write that fails never lands locally either, so the phone can't show a plant the account doesn't have.
  4. Photos go to a private Storage bucket under the user's own folder. The app asks for a fresh signed URL to display one - there is no permanent public link.
  5. Signing out wipes the mirror. Deleting the account cascades the rows and clears the bucket.

Row-level security is what makes the direct app-to-database path safe: every policy on plants and on the photo bucket checks the row against the caller's own user id, so the app can only ever read and write its own.

How the scraper adapts to each site

Every nursery's website is built on one of a handful of platforms, and each platform has its own search URL and its own markup. Rather than one scraper trying to parse every possible layout, the pipeline first figures out which platform a site is running, then uses the URL pattern that platform already supports.

  1. Fingerprint the homepage. The scraped markdown/HTML is checked for tells: cdn.shopify.com or /products/ means Shopify, wp-content or /product-category/ means WooCommerce, wixstatic.com means Wix.
  2. Reuse a known search pattern. Each platform maps to a search-URL template - Shopify is /search?q=, WooCommerce is /?s=&post_type=product, Wix is /search?q=. Recognizing the platform means the scraper already knows the right URL to hit, no guessing per site.
  3. Retry with the rendered page. Some storefronts build their markup client-side, so a static fetch shows nothing recognizable. If the first pass comes back unknown, the scraper re-fetches with JS rendering turned on.
  4. Ask OpenAI as a last resort. If the platform is still unrecognized, the page's scripts/CDN hints are handed to OpenAI to classify and to guess a search URL. That answer is saved to disk, so the same unfamiliar platform is never paid to classify twice.

Knowing the platform also decides who reads the page. Shopify and WooCommerce send a finished page, so Tavily fetches it as-is in well under a second. A storefront that builds itself in the browser has to be rendered, and only Firecrawl does that - so it leads there, with Tavily as the rescue if it fails.

That split is most of a recent speed win: a search went from 81s to 36.5s, and healthy shops from 26-41s each to about a second. The cause was never how many sites were read at once - it was that the renderer allows ten requests a minute, and a refused read looks exactly like an unrecognized platform, which is the path that spends three more requests on the same shop. The limit was feeding itself.

How we know it is working

GET /health answers the questions that are otherwise invisible until they show up on a bill or in a bad review. Two of them cost money to get wrong:

  1. Is the shared scrape cache actually on? Without its Supabase credentials the cache quietly answers "miss" forever. Nothing breaks, no error is logged, and every single search becomes a live paid scrape. cache.enabled says so directly rather than leaving it to be inferred from the bill.
  2. Has a nursery stopped parsing? A shop whose markup changed returns nothing forever while the search as a whole still succeeds - the results are simply quietly shorter. Each site's read is tracked, and a site we have failed to read several times running is flagged. A shop that we read fine and that merely does not stock the plant is not a fault and is never flagged.
  3. Which providers are answering? lastSuccess carries the last good call to each of PlantNet, the health assessment, and the nursery scrape, so an outage is visible without waiting for a user to hit it.

The summary is public. The per-site detail and the recent-failure ring need the shared secret - an unauthenticated endpoint should not enumerate which shops we scrape or which of them are currently down.
